# Проверка 0.4.0

## Существующий сетевой путь

На Windows 11 подтверждён ручной сценарий версии 0.3.3: встроенные usque/winws → HTTPS-шлюз → SSH → VPS AmneziaWG → полный профиль AmneziaVPN. Внешние системный WARP и zapret были отключены пользователем. Браузер и Discord работали; прямой HTTPS-запрос показывал выход через VPS, тестовая загрузка завершилась.

Каталог Flowseal загружен и проверен. В одной тестовой сети работал вариант `general (FAKE TLS AUTO ALT2) · TLS 2`. Это результат конкретного теста, не рекомендация универсальной стратегии. Личные IP/домены, профили, ключи и журналы в отчёт не включены.

## Автоматические проверки 0.4.0

- C# unit tests: существующие профили, SSH fingerprint, UDP framing, экспорт VPN, шлюз, обновления, строгий импорт стратегий и Flowseal.
- Приглашения: шифрованный roundtrip, случайность salt/nonce, неверный пароль, изменение ciphertext, неизвестная версия, размер, обязательные поля, запрещённые VPN hooks, отдельная схема без административных полей.
- Python: ограниченный обработчик через реальные stdin/stdout-кадры, сокрытие чужих peer, отказ административных команд/чужих endpoint и telemetry, игнорирование SSH_ORIGINAL_COMMAND, отзыв открытого сеанса.
- Изменения ключей/конфигурации: сохранность посторонних строк authorized_keys, запрет traversal в ID и удаление только указанного VPN peer.
- Windows GUI startup smoke test; сборка установщика и архивов с allowlist; проверка публикационных входов и payload на секреты/личные маркеры.

Python-тесты сетевых компонентов выполняются также на Linux в CI. Локальный Windows-прогон не заменяет Linux-проверку файловых прав и flock. Тесты используют синтетические данные и не требуют рабочего VPS.

## Что ещё проверять внешнему тестировщику

Новая передача приглашений не объявляется проверенной на всех реальных VPS. Передача между двумя людьми и конкретными установками AmneziaVPN остаётся приёмочным тестом PoC:

1. Владелец создаёт приглашение; программа должна подтвердить ограниченный SSH-вход перед сохранением файла.
2. Второй компьютер импортирует файл; список серверов владельца и его административные секреты не должны передаваться.
3. Получатель регистрирует своё WARP-устройство, подключает мост, импортирует свой `.conf` и проверяет внешний IPv4, сайты, голос, DNS/IPv6.
4. Владелец отзывает приглашение; проверяется прекращение текущего сеанса, невозможность нового SSH/моста и отсутствие peer в AWG после перезапуска сервера.
5. Отдельно проверяются отмена/обрыв во время создания, занятый локальный порт, неверный пароль и повторный импорт.

Не заявлены: независимый аудит безопасности, гарантированное отсутствие DNS/IPv6-утечек, kill switch, устойчивость к DoS, неограниченное число получателей, производительность во всех сетях или совместимость любых конфигураций AWG.
