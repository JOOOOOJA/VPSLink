# Приглашения: владелец и получатель

Экспериментальная функция 0.4.0. Требуется существующий поддерживаемый AmneziaWG, профиль владельца с проверенным SSH fingerprint и входом root. При ограничении административного SSH принудительной командой/хешем старого relay администратор должен отдельно обновить разрешённый код. VPSLink не снимает такие ограничения автоматически.

## Порядок работы

Владелец сначала подключает свой сервер и завершает его обычную настройку. Для управления приглашениями затем самостоятельно отключает AmneziaVPN и мост. Вкладка «Приглашения» не останавливает сеть за пользователя; при активном VPN/ядре проверка отказывается запускаться. Встроенный WARP требует административного запуска VPSLink.

«Создать приглашение…» запрашивает имя получателя, пароль (12–256 символов, с повтором) и путь `.vpslink`. Программа генерирует новые X25519-ключи VPN и отдельный ED25519 SSH-ключ, добавляет нового peer, устанавливает принудительную SSH-команду, проверяет вход этим ключом и только после этого записывает зашифрованный файл. Приватный SSH-ключ создаётся в временном каталоге с ACL текущего пользователя и удаляется после операции. Приватный VPN-ключ генерируется на компьютере владельца.

Получатель импортирует файл через ту же вкладку и сверяет адрес/SSH fingerprint с владельцем по доверенному каналу. Импорт не подключает VPN и не включает автозапуск. Встроенный режим требует **своей** регистрации WARP: «Серверы → Изменить → Путь до VPS». После подключения моста нужно сохранить `.conf`, импортировать в совместимую AmneziaVPN и включить. По умолчанию локальный порт приглашения — 39609; если занят, его меняют в настройках и заново экспортируют `.conf`.

Импортированному профилю недоступно создание приглашений и настройка Cloudflare. Копия одного приглашения на двух устройствах использует один VPN peer; для независимого отзыва создавайте отдельные приглашения.

## Что передаётся

Отдельная схема `Invitation`, версия 1:

- ID и название приглашения;
- адрес/порт SSH и ED25519 fingerprint;
- новый ограниченный приватный SSH-ключ получателя;
- HTTPS-relay URL и его bearer-токен, если используется;
- необходимость встроенного WARP, удалённый UDP endpoint, ID интерфейса;
- публичный ключ нового peer и его нативная VPN-конфигурация.

Не передаются административный SSH-пароль/ключ владельца, его VPN-профиль, Cloudflare API/connector-токены, WARP-регистрация, локальные пути/адаптеры, автозапуск и внутренний Profile JSON. После импорта секреты защищаются DPAPI нового пользователя Windows. На исходном устройстве .NET строки могут оставаться в памяти до сборки мусора; гарантия полного стирания памяти не заявляется.

Конверт `VPSLinkInvitation` содержит version, salt, nonce, ciphertext, tag. AES-256-GCM, 16-байтовая соль, 12-байтовый nonce, 16-байтовый tag; PBKDF2-HMAC-SHA256 с 310000 итерациями; AAD `VPSLink invitation v1`. Алгоритмы/число итераций заданы версией, не берутся из входного файла. Максимальный входной файл — 256 KiB. Изменение ciphertext/tag и неверный пароль отвергаются. VPN hooks PreUp/PostUp/PreDown/PostDown не допускаются. Зашифрованный файл и пароль вместе дают полный доступ получателя; пароль следует передавать отдельно.

## Серверное ограничение полномочий

Создаются `/root/.vpslink-shares/<id>/record.json`, `policy.json`, `relay.py`, `client.py`. Каталоги 0700, файлы 0600; ID — ровно 32 hex-символа. В root `authorized_keys` добавляется только строка отдельного ключа с:

```text
restrict,command="/usr/bin/python3 -I /root/.vpslink-shares/<id>/client.py" ssh-ed25519 <public-key> vpslink-share-<id>
```

`restrict` запрещает forwarding/PTY/agent/X11/user rc. SSH_ORIGINAL_COMMAND игнорируется. `python3 -I` не принимает Python-настройки окружения пользователя. Обработчик запускается из установленного root-владельцем файла, **не исполняет присланный код** и допускает лишь:

- `I`: информацию только о разрешённом VPN и одном peer;
- `S`: точное совпадение UDP host/port с политикой;
- `T`: точное совпадение interface ID и public key получателя;
- `D`, `P`: датаграммы к закреплённому endpoint и heartbeat.

Команды `C`, `G`, `J`, неизвестные кадры, иной endpoint или чужой peer закрывают сеанс. SSH-ключ не даёт shell-доступа. Однако обработчик имеет root-права для чтения статистики AWG: уязвимость обработчика потенциально затрагивает root. Это не изоляция отдельным Linux-пользователем/контейнером, не квота и не защита от ресурсного DoS. VPN-сегментация и доступность других адресов/клиентов определяются firewall владельца VPS. Не используйте PoC как готовую многопользовательскую коммерческую платформу.

HTTPS-relay bearer-токен общий для данного шлюза. Его наличие даёт доступ к SSH-входу, но не аутентификацию SSH. Отзыв приглашения не ротирует общий relay-токен: бывший получатель может обращаться к входу SSH, но его ключ больше не разрешён. Отдельные токены шлюза/квоты на пользователя в этой версии не реализованы.

## Отзыв и восстановление

«Обновить список» читает серверные записи, включая отозванные. «Отозвать выбранное…» сначала удаляет активную политику и свою строку SSH-ключа, затем удаляет точный peer из сохранённого конфига и runtime AWG. Другие строки `authorized_keys` и peer не перезаписываются целиком. Изменения конфига проверяют исходный хеш; операции Link сериализованы файловыми блокировками.

Открытый сеанс проверяет наличие политики на каждом входящем кадре. Обычно heartbeat прекращает его в течение нескольких секунд; уже переданный трафик отозвать невозможно. Запись `record.json` остаётся для учёта/повторного отзыва. Если удаление peer не подтверждено, UI сообщает, что **прямой VPN-доступ мог сохраниться**. Повторите отзыв, а при изменении контейнера/пути конфига удалите peer в актуальном серверном VPN вручную.

Если связь оборвалась при создании или файл не записался, обновите список: сервер мог успеть добавить клиента. Отзовите незавершённое приглашение перед созданием нового. После аварийного завершения между добавлением VPN peer и сохранением recovery-записи может остаться лишний peer: владелец проверяет конфигурацию AWG. Полной распределённой транзакции между Windows, файловой системой VPS и VPN runtime нет.

Для ручного аварийного отзыва администратор удаляет `policy.json` нужного ID и строку с его точным маркером из `authorized_keys`, затем соответствующий VPN peer из сохранённой конфигурации и runtime. Не удаляйте все SSH-ключи или весь контейнер. После перезапуска VPS ограничения сохраняются в файлах, а peer — в конфигурации VPN.
