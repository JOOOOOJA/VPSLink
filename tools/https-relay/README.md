# SSH через HTTPS

Для VPS с nginx и действующим TLS-сертификатом. Шлюз принимает запрос по указанному адресу и соединяет его с SSH на loopback. У пользователя по-прежнему должны быть учётные данные SSH и проверенный отпечаток ED25519.

На VPS передайте в `install.py` путь к файлу виртуального хоста nginx и имя, на которое выдан сертификат.

```sh
sudo python3 install.py /etc/nginx/sites-available/example example.com
```

Скрипт ищет одну пару директив `listen 443 ssl…` и `server_name example.com;` в этом порядке. Он создаёт службу `tfl-https-relay` на `127.0.0.1:18091`, проверяет конфигурацию и перезагружает nginx. Исходная конфигурация сохраняется в `/etc/tfl-https-relay/nginx.original`. При ошибке установки скрипт возвращает конфигурацию и удаляет созданную службу.

Добавьте `https://example.com/link-ssh` и токен из `/etc/tfl-https-relay/token` в профиль Windows. Передайте токен по защищённому каналу. Служба пропускает соединение только после проверки токена и направляет его только на локальный SSH. Извне используйте TLS с действующим сертификатом.

После удаления строки `include /opt/tfl-https-relay/nginx-location.conf;` из этого виртуального хоста выполните `nginx -t`, перезагрузите nginx и остановите службу командой `systemctl disable --now tfl-https-relay`.

HTTPS-шлюз может работать без WARP, если Windows уже может напрямую соединиться с адресом HTTPS. Маршрут до адреса шлюза должен оставаться доступным при включении системного VPN. Системные правила WARP и другие политики Windows продолжают действовать.

## WebSocket и Cloudflare Tunnel

Текущий `relay.py` принимает также стандартный WebSocket Upgrade. Для него укажите в Link `wss://example.com/link-ssh` с тем же токеном. Существующий nginx location передаёт оба варианта Upgrade. Незашифрованные адреса `ws://` не принимаются.

Можно направить Cloudflare Tunnel на loopback-адрес relay: тогда клиент соединяется с адресом Cloudflare вместо заблокированного IP VPS. Токен relay и проверка ключа SSH обязательны и в этом режиме. Relay не предоставляет доступ к произвольным адресам: единственная цель — локальный SSH.

Quick Tunnel подходит для временного испытания: адрес меняется при новом запуске, гарантий доступности нет. Начиная с 0.2.6 кнопка **Постоянный шлюз…** в Link создаёт именованный Cloudflare Tunnel, DNS-запись и устанавливает cloudflared автоматически. Для первоначальной настройки всё равно нужен хотя бы один рабочий административный канал до VPS.

## Постоянный шлюз через Link 0.2.6

Нужны активная зона Cloudflare, свободное имя вроде `link.example.com` и API-токен с `Account / Cloudflare Tunnel / Edit`, `Zone / DNS / Edit`, `Zone / Zone / Read`. Ограничьте токен своим аккаунтом и нужной зоной. Токен вводится в маскированное поле и используется только на время настройки. Link не заменяет чужую DNS-запись и проверяет принадлежность повторно используемого туннеля.

На Linux x64 VPS с systemd мастер создаёт `thingsnotfun-link-relay.service` и `thingsnotfun-link-cloudflared.service`. Relay слушает только `127.0.0.1:18093`; cloudflared соединяется с Cloudflare по HTTP/2. Обе службы включены в автозапуск и настроены на восстановление после сбоя. Исполняемый файл cloudflared проверяется по закреплённому SHA-256. Предыдущий временный шлюз и nginx не изменяются.

Программные файлы находятся в `/opt/thingsnotfun-link-gateway`, закрытые данные — в `/etc/thingsnotfun-link-gateway`. Секреты передаются службам через systemd credentials. На VPS остаются отдельные токены соединения и конкретного туннеля, а не API-токен управления Cloudflare. Link активирует новый адрес только после успешного SSH-подключения с проверкой прежнего отпечатка сервера. Для дальнейших подключений повторный ввод API-токена не нужен.
